# Agentic Architecture Principles

## 1. Dynamic Rule Injection (No Hardcoded Bureaucracy)

**Principle:** Do NOT hardcode extensive organizational rules, clauses (e.g., CVC circulars), or financial limits (e.g., DOP limits) inside the Python tool logic via massive `if/else` dictionaries. 

**Why:** Government organizations and massive enterprises have thousands of rules and limits that change constantly. Hardcoding them is impossible to maintain and scales poorly.

**How it should work:**
1. The LLM uses **RAG** (Retrieval-Augmented Generation) to read the actual PDF manuals, SOPs, and Circulars.
2. The LLM extracts the *applicable clause* and the *required financial limit* based on the context of the user's request.
3. The LLM passes these extracted strings directly into the Python tool via strict Pydantic schemas (e.g., `applicable_cvc_clause="Clause 4.1"`, `required_authority="Director"`).
4. The Python tool's job is solely to enforce boolean logic (e.g., "If it is single-source, ensure the LLM provided an emergency flag and a valid clause") and to securely log the transaction, NOT to be a database of rules.

## 2. Ubiquitous Cryptographic Auditing (Audit Ledger Integration)

**Principle:** EVERY deterministic Python tool built for this workbench MUST integrate the `AuditLedger` from `tools/audit_trail.py`.

**Why:** The workbench operates in highly confidential, heavily regulated industrial and government environments (PSUs, refineries). Every single calculation, financial decision, or security check made by the AI must have immutable cryptographic provenance to withstand statutory audits (CAG/CVC/ASME).

**How it should work:**
1. Every tool class must accept a `use_audit_trail: bool = True` parameter in its constructor.
2. If enabled, the tool must instantiate `self.ledger = AuditLedger()`.
3. Before returning the final result to the AI Agent (e.g., in the `evaluate()` or `calculate()` method), the tool MUST call `self.ledger.append_event(...)`.
4. The event MUST record:
   - `event_type` (e.g., 'CALCULATION', 'COMPLIANCE_CHECK', 'EXTRACTION')
   - The exact `inputs` provided by the LLM/User.
   - The exact `outputs` generated by the tool.
   - A `status` flag (e.g., 'APPROVED', 'CRITICAL_BREACH', 'BLOCKED_BY_COMPLIANCE').
